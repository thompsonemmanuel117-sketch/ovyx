# OVYX Stage 6 — Project and Workspace Management

**Status:** Implementation candidate on `stage-6/workspace-management`; full acceptance and merge are pending.  
**Scope:** Non-Web-Studio project and workspace management. Web Studio is excluded.

## Existing project system retained

The existing `ProjectStore` remains the client-side source of truth for projects. The existing Projects route and its create, open, duplicate, delete, recovery, status and update-date experiences are retained. The new workspace layer does not replace the project store, Firebase identity, account-scoped local cache or the existing project sync engines.

## Workspace model

A workspace is an owner-managed container for projects.

- Firestore path: `users/{firebaseUid}/workspaces/{workspaceId}`.
- The deterministic `personal` workspace is provisioned lazily for an account.
- Additional workspace IDs are generated by the server.
- Workspace records carry the owner UID and normalized owner email; the API verifies both on reads and writes.
- Workspace actions are authenticated and server-authoritative: list, create, rename/update, archive and restore.
- The default personal workspace cannot be archived.
- Workspace updates use Firestore update-time preconditions to reject stale writes.
- Workspaces are archived, not hard-deleted, so project references are not silently orphaned.

## Project association and legacy compatibility

Projects remain stored in the existing account-scoped Firestore collection at `users/{email}/projects/{projectId}`. A project now carries a `workspaceId` association.

- Existing project documents without `workspaceId` are interpreted as belonging to `personal`.
- No bulk migration or destructive rewrite of existing projects is required.
- `GET /api/projects?workspaceId=...` returns only projects owned by the authenticated Firebase UID/email pair in that workspace.
- `GET /api/projects?projectId=...` returns one owner-verified project detail record.
- Project writes preserve the existing owner checks and Firestore update-time preconditions.
- Writes into archived workspaces are rejected; archived workspace projects remain readable for recovery and restore.

## Client experience

The existing accessible project picker is extended into a workspace-aware switcher.

- Workspace selection is stored per Firebase UID, never as one global account-agnostic preference.
- The project list is filtered to the selected workspace.
- Project search includes project name, description and status.
- Project rows expose status, page count, description and last saved/updated date.
- Users can create, rename, archive and restore workspaces from the same dialog.
- Existing project creation is reused. New projects inherit the selected workspace through the existing `ProjectStore.save()` path.
- Opening a project restores the selected workspace from that project's association.
- Archived workspaces remain selectable for inspection, but project creation is disabled there.
- The UI uses the existing ProjectStore open/create/save operations rather than a second project database.

## Collaboration boundary

The current repository does not contain a verified workspace membership, invitations, team-role or multi-user collaboration model. This stage therefore exposes owner-managed workspaces only and explicitly reports collaboration as unsupported. It does not render fake invite/member controls or grant access based on client-supplied identities. Team collaboration remains out of scope until a complete server-authoritative membership and permission model exists.

## Acceptance checks

- Workspace API: authenticated owner checks, default workspace provisioning, create, rename, archive, restore, default-workspace archive rejection and stale-write protection.
- Project API: legacy project-to-personal mapping, workspace-scoped inventory and detail reads, cross-account isolation, archived read-only behaviour and project association on save.
- Browser: desktop and mobile workspace switching, filtered project lists, search, rename, archive/restore, creation, project-to-workspace assignment, project opening and existing create-flow handoff.
- Regression: existing ProjectStore, Firebase, account isolation, project sync, project recovery, Settings, Admin and Web Studio tests remain intact.
- Production: merged commit deployed, app shell/runtime health verified, and the deployed workspace/project flows smoke-tested.

A successful branch build or PR merge alone does not complete Stage 6. Stage 6 remains open until all applicable acceptance checks pass and the completed implementation is merged into `main`.
